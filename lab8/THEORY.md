## 1. Что такое канал

Канал — это **типизированная труба между горутинами** и одновременно **точка синхронизации**.

```go
ch := make(chan int)      // нулевое значение канала — nil, поэтому всегда make
ch <- 42                  // отправить
v := <-ch                 // принять
v, ok := <-ch             // ok == false: канал закрыт И пуст
close(ch)                 // «больше ничего не будет»
```

- **Ссылочный тип**, как map. `make` создаёт структуру `hchan` в куче, переменная хранит указатель на неё. Передача в функцию копирует указатель, и обе стороны работают с одним каналом.
- **Направления:** `chan<- int` только отправка, `<-chan int` только приём. Компилятор проверяет: из send-only нельзя читать, в receive-only нельзя писать, и **receive-only нельзя закрыть**. Обычный `chan int` неявно приводится к любому направлению при передаче. Обратно — нет.
- **«Don't communicate by sharing memory; share memory by communicating».** Вместо общей переменной под мьютексом данные передаются по каналу. В каждый момент значением владеет одна горутина: отправитель отдал, получатель получил.

## 2. Как канал устроен внутри

```go
type hchan struct {
    qcount   uint           // сколько значений сейчас в буфере   (= len(ch))
    dataqsiz uint           // размер буфера                      (= cap(ch))
    buf      unsafe.Pointer // кольцевой буфер на dataqsiz элементов
    elemsize uint16
    closed   uint32
    sendx    uint           // куда писать в кольце
    recvx    uint           // откуда читать
    recvq    waitq          // очередь ждущих получателей (sudog)
    sendq    waitq          // очередь ждущих отправителей
    lock     mutex          // всё выше защищено этим мьютексом
}
```

**Отправка `ch <- v`** (под `lock`):
1. Канал закрыт → `panic: send on closed channel`.
2. В `recvq` есть ждущий получатель → значение копируется **прямо в его стек**, минуя буфер (direct send), получатель помечается готовым (`goready`).
3. В буфере есть место → копия в `buf[sendx]`, `sendx++`, возврат.
4. Иначе горутина заворачивается в `sudog`, встаёт в `sendq` и паркуется (`gopark`). Поток ОС не блокируется: планировщик берёт следующую горутину.

**Приём `<-ch`** — симметрично. Если в `sendq` кто-то ждёт, а буфер полон, получатель берёт значение из **головы** буфера, а значение ждущего отправителя кладёт в **хвост**. Так сохраняется FIFO. Если канал закрыт и буфер пуст → нулевое значение, `ok = false`.

**`close(ch)`**: `closed = 1`, потом **все** ждущие получатели просыпаются (получат ноль и `false`), **все** ждущие отправители просыпаются и паникуют.

**nil-канал**: `hchan` нет. Отправка и приём сразу паркуют горутину навсегда (`gopark` без очереди, будить некому).

Отсюда: канал — это мьютекс, кольцевой буфер и две очереди ожидания. Поэтому операция стоит ~20 нс, а с переключением горутины ~80 нс (раздел 11).

## 3. Таблица: nil / open / closed

| Операция | nil | открытый | закрытый |
|---|---|---|---|
| `ch <- v` | блок навсегда | ждёт получателя / место в буфере | **panic: send on closed channel** |
| `<-ch` | блок навсегда | ждёт значение | остаток буфера, потом **сразу** `0, false` |
| `close(ch)` | **panic: close of nil channel** | OK | **panic: close of closed channel** |
| `len`, `cap` | 0, 0 | значений в буфере / размер | осталось / размер |

Проверено в `go run ./task1 table`:
- **panic** — нарушение правил программистом (3 ячейки). Ловится `recover`.
- **«блок навсегда»** превращается в `fatal error: all goroutines are asleep - deadlock!`, только если **больше никто** не может работать. Это `fatal error`, `recover` не поможет. В трассировке видно `[chan send (nil chan)]` или `[chan receive]`.
- **Полезные ячейки:** закрытый канал всегда готов к чтению (поэтому `close` — это broadcast), nil-канал никогда не готов (поэтому `ch = nil` выключает кейс в `select`).

**Почему runtime видит deadlock в `main`, но не в сервере.** Проверка `checkdead` глобальная: «нет ни одной горутины, которая может проснуться: ни готовых, ни таймеров, ни сети, ни syscall». В сервере всегда кто-то ждёт сеть (`Accept`) или таймер, поэтому застрявшая горутина в хендлере — тихая утечка. С Go 1.26 есть профиль `goroutineleak`. Он через GC ищет горутины, заблокированные на каналах, до которых никто не может дотянуться (`go run ./task1 leakprofile`, `/debug/pprof/goroutineleak`).

## 4. Небуферизованный и буферизованный канал

| | Небуферизованный `make(chan T)` | Буферизованный `make(chan T, n)` |
|---|---|---|
| Отправка ждёт… | пока получатель заберёт | только если буфер полон |
| Приём ждёт… | пока придёт отправитель | только если буфер пуст |
| Когда `ch <- v` вернулся, известно… | **значение получено** | значение **лежит в очереди** |
| Аналогия | передать книгу из рук в руки | бросить письмо в почтовый ящик |

**Гарантии модели памяти Go** (это и делает канал инструментом синхронизации, а не просто очередью):
1. Отправка **happens-before** завершения соответствующего приёма. Всё, что отправитель записал до `ch <- v`, видно получателю после `<-ch`.
2. Для **небуферизованного** ещё и наоборот: приём happens-before завершения отправки. Отправитель после `ch <- v` знает, что получатель дошёл до `<-ch`.
3. `close` happens-before приёма, который вернулся из-за закрытия. Поэтому `close(done)` безопасно «публикует» всё, что сделано до него.
4. k-й приём из канала ёмкости C happens-before завершения (k+C)-й отправки. Так буферизованный канал работает как **семафор** на C мест.

**Время отправки** (`go run ./task2 run`, получатель занят 300 мс, потом берёт значение раз в 100 мс): отправка `k` возвращается в 0s, если `k ≤ cap`, иначе в `300 + (k−cap−1)·100` мс. Буфер позволяет отправителю уйти вперёд на `cap` значений, но **средняя скорость определяется медленной стороной**.

**Буфер не лечит deadlock.** Он откладывает его до момента, когда значений станет больше, чем слотов. Размер буфера выбирают по причине:
- `1` — «ровно один результат, который могут не забрать» (fix утечки `fetchLeaky`);
- `N` — по числу воркеров или отправок, которые могут случиться без читателя;
- небольшой — сгладить короткие всплески.

**`len(ch)` устаревает в момент чтения.** Его можно использовать для мониторинга и тестов. Для решений «если есть место — отправлю» нужен `select` с `default`.

## 5. close, range и владение

```go
for v := range ch { ... }   // заканчивается, когда ch закрыт И пуст
v, ok := <-ch               // ok == false: закрыт и пуст
```

Узнать, закрыт ли канал, **не читая** из него, нельзя (функции `isClosed` нет, и это сознательное решение: ответ устарел бы мгновенно). Закрытие **не выбрасывает** буфер: получатель сначала дочитает всё, потом увидит `ok == false`.

**Правила закрытия:**
1. **Закрывает только отправитель.** Получатель не знает, будут ли ещё значения, а отправка в закрытый канал — паника.
2. **Закрывают один раз.** Второй `close` — паника.
3. **Закрывать не обязательно.** Закрытие — это сообщение «конец потока», и нужно оно тем, кто ждёт конца (`range`, `ok`). Незакрытый канал без ссылок соберёт GC.

**Владелец канала** — горутина, которая его создаёт, пишет в него и закрывает. Владелец возвращает `<-chan T`: компилятор запретит остальным писать и закрывать.

```go
func generator(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)          // владелец закрывает ровно один раз
        for _, n := range nums { out <- n }
    }()
    return out
}
```

**Много писателей: кто закрывает?** Никто из них. Если каждый писатель закрывает канал, первый закончивший закроет его, и остальные получат `send on closed channel`. Иногда двое закончат одновременно, и будет `close of closed channel` (task3 wrong: 8 из 200 запусков). Правильно — отдельная горутина-закрыватель:

```go
go func() {
    wg.Wait()       // все писатели закончили...
    close(results)  // ...теперь закрывать безопасно
}()
return results
```

Она **обязана** быть отдельной горутиной. Если вызвать `wg.Wait()` до `return`, писатели висят на небуферизованной отправке, читатель получит канал только после `return`, и получается deadlock (`go run ./task3 closeinline`).

## 6. Конвейеры (pipelines)

Конвейер — это цепочка стадий, соединённых каналами. Каждая стадия:
- читает `in` до закрытия (`for v := range in`),
- пишет в **свой** `out`,
- делает `defer close(out)`.

```go
sum(filterEven(square(generator(1, 2, ..., 10))))   // 220
```

Почему добавление стадии ничего не ломает: у стадий одинаковая форма `func(<-chan T) <-chan T`, и они не знают о соседях. Сигнал «конец» проходит по цепочке сам: каждый `close` заканчивает `range` следующей стадии.

**Fan-out / fan-in:** несколько воркеров читают один канал (fan-out, работу делят между собой), а их результаты сливаются в один канал (fan-in, `merge` или горутина-закрыватель с `WaitGroup`). Это и есть worker pool из Task 6.

**Проблема конвейеров — ранний выход потребителя.** Если `sum` вернётся раньше (ошибка, нашли что искали), верхние стадии повиснут на `out <-` навсегда. Решение — канал `done` (раздел 8), см. пост «Pipelines and cancellation» в Go Blog.

## 7. select

```go
select {
case v := <-a:      ...
case b <- 42:       ...
case <-time.After(100 * time.Millisecond): ...
default:            ...   // необязательно: делает select неблокирующим
}
```

- Ждёт, пока **один** из кейсов сможет выполниться, и выполняет его.
- **Несколько готовы → выбор случайный** (равномерный). Runtime (`selectgo`) каждый раз перемешивает порядок проверки (`pollorder`). Каналы блокируются в порядке адресов (`lockorder`), чтобы не было взаимной блокировки двух `select`. Измерено: 506/494, 519/481, 484/516. Порядок в тексте **ничего не значит**.
- **Ни один не готов, нет `default`** → горутина встаёт в очереди **всех** каналов из кейсов и паркуется. Первый сработавший будит её, из остальных очередей она убирается.
- **С `default`** → никогда не блокируется. `default` выполняется, только если **ни один** кейс не готов. Закрытый канал готов всегда, поэтому `default` при нём не сработает ни разу (bonus: 1000/1000).
- **`select {}`** без кейсов блокирует навсегда.
- **Выражения во всех кейсах вычисляются заранее**, один раз, при входе в `select`: `time.After(...)` создаёт таймер, даже если сработал другой кейс. Поэтому в цикле лучше `time.NewTimer` + `Stop`/`Reset`.

**Приоритет** через два `select`: первый только с нужным каналом и `default`, второй со всеми. Приоритет нестрогий, и есть риск starvation для второго канала.

**nil выключает кейс.** Кейс на nil-канале не бывает готов никогда. В `merge`, когда `a` закрылся, пишут `a = nil`, и select больше на `a` не смотрит. Без этого закрытый `a` готов **всегда**, select полкруга тратит на `0, false`, и цикл крутится вхолостую со 100% CPU (120–190 тыс. холостых итераций за ~6 мс в `mergenonil`). Тот же приём: включить кейс отправки только когда есть что отправлять (`var out chan T; if len(pending) > 0 { out = realOut }`).

**Неблокирующая отправка / приём:**

```go
select {
case queue <- job:   // поставили
default:             // очередь полна — сбросить, посчитать, ответить ошибкой
}
```

## 8. Остановка горутин: done и context

Закрытие канала будит **всех** его получателей сразу. Поэтому закрытый `chan struct{}` — идеальный сигнал «стоп» для любого числа горутин:

```go
select {
case jobs <- w:
case <-done:     // потребитель сдался — выходим
    return
}
```

Правило: **каждая блокирующая операция** горутины, которая может так и не завершиться (отправка в канал, который могут перестать читать, или ожидание данных, которые могут не прийти), должна быть в `select` с `<-done`. В Task 6 без этого остались 6 горутин: producer на `jobs <-`, 4 воркера на `results <-` и closer на `wg.Wait()`. С `done` осталась 1 (`main`).

`context.Context` — это тот же паттерн: `ctx.Done()` возвращает канал, который закрывается при `cancel()` или дедлайне. Плюс `ctx.Err()` объясняет причину, контексты наследуются (отмена родителя отменяет детей), и можно передавать значения запроса. В реальном коде — `context`, `done` — для понимания механики.

## 9. Таймауты и утечки

```go
select {
case r := <-slow:
case <-time.After(100 * time.Millisecond):   // перестали ЖДАТЬ, но не остановили РАБОТУ
}
```

**Таймаут в select останавливает ожидание, а не работу.** Если горутина, которая считает `slow`, отправляет в небуферизованный канал, после таймаута она повиснет навсегда (Week 8). Варианты:
- **буфер 1** — горутина положит результат и выйдет. Работа всё равно делается до конца;
- **отмена** — передать `done`/`ctx` внутрь работы, чтобы она прервалась;
- оба вместе (Week 8, Task 6 `ctx`).

Буфер должен вмещать **все** отправки, которые горутина может сделать без читателя. Для двух отправок буфера 1 мало (`go run ./task2 fetch`: 100 из 100 утекли).

**Как заметить утечку:** `runtime.NumGoroutine()` растёт; профиль `goroutine` (`/debug/pprof/goroutine?debug=1`) показывает тысячи одинаковых стеков на `chan send`; профиль `goroutineleak` (Go 1.26+); тест «NumGoroutine до и после» (есть в task3, task4, task5, task6).

**Утечка ≠ «горутина ещё работает».** Сразу после 1000 таймаутов в `task5 fetch` живы ~44 горутины, но через 100 мс их 0. Утечка — это горутина, которая не закончится **никогда**.

## 10. Backpressure

**Backpressure** (обратное давление) — это когда медленный потребитель замедляет производителя: давление «отдаёт назад» по конвейеру. **Ограниченный канал даёт его бесплатно:** полный буфер заставляет `ch <- v` ждать.

Эксперимент (producer ~5 задач/мс пачками, consumer 1 задача/мс, 2000 задач, `go run ./task6 backpressure`):

| Стратегия | Producer | Память (очередь) | Потеряно | Задержка задачи |
|---|---|---|---|---|
| **block** (буфер 10) | замедлен до 1/мс (2.27 с) | 10 | 0 | ≤ 10 мс |
| **huge** (буфер 2000) | не ждёт (0.4 с) | **1656** | 0 | **до 1.89 с** |
| **drop** (буфер 10 + `default`) | не ждёт (0.4 с) | 10 | **1646** | ≤ 10 мс |
| **wait + timeout** (`Submit`) | ждёт до таймаута | ограничена | отказ с ошибкой | ограничена |

**Три (четыре) реакции на полную очередь:**
1. **Block** — ждать. Никто не теряется, задержка ограничена, но тормозит производитель. Хорошо внутри конвейера и для фоновых задач.
2. **Drop** — выбросить (`select` + `default`). Производитель не ждёт, но данные теряются. Хорошо для метрик, логов, событий «последнее значение важнее».
3. **Wait with timeout → error** — ждать немного, потом вернуть ошибку (`ErrQueueFull` → HTTP 503 + `Retry-After`). Короткие всплески проходят, при перегрузке клиент быстро узнаёт об отказе. Лучший вариант для серверов.
4. (Анти-вариант) **неограниченная очередь**.

**Почему большой буфер — не решение медленного потребителя.** Он не увеличивает пропускную способность (потребитель всё так же делает 1/мс), а только прячет перегрузку:
- задержка растёт линейно с очередью: запрос ждёт 1.89 с, клиент уже ушёл, а сервер всё равно потратит на него CPU;
- если поток не кончается, очередь растёт без предела, потом OOM, и падают **все** запросы;
- производитель, клиент и балансировщик не получают сигнала «притормози» или «иди к другому серверу».

Буфер решает только **временную** разницу скоростей (всплески). Постоянную разницу решают только ускорение потребителя (больше воркеров) или ограничение входа (block/drop/503).

## 11. Сколько стоит канал

Task 7: 10 000 `int` от одной горутины к другой, M4:

| | на значение (`-cpu 1`) | (`-cpu 2`) | B/op |
|---|---|---|---|
| `buf=0` | 77 нс | 86 нс | 128 |
| `buf=1` | 57 нс | 64 нс | 144 |
| `buf=100` | 18 нс | 24 нс | 1 040 |
| `buf=10000` | 16.5 нс | 20 нс | 81 936 |
| пачки по 100 | 1.8 нс | 1.8 нс | 89 752 |
| без канала | 0.23 нс | 0.23 нс | 0 |

- **Небуферизованный медленнее всех:** каждое значение — rendezvous, одна сторона паркуется, другая будит, переключение горутины на **каждое** значение.
- **Буфер 100:** переключение раз в ~100 значений, остаётся цена lock + copy + unlock (~18 нс).
- **Буфер 10 000:** почти то же время (−10%), но 80 КБ памяти на каждый вызов. Отдача от роста буфера быстро кончается.
- **`-cpu 2` медленнее:** стороны на разных ядрах дерутся за `hchan.lock`, кэш-линия прыгает между ядрами, будить чужой P дороже.
- **Пачки ~10× быстрее:** операций с каналом в 100 раз меньше, цена канала делится на 100 значений. Новый слайс на каждую пачку: после отправки им владеет получатель.

Вывод: канал — это ~20–80 нс на операцию. Для координации это дёшево, для передачи миллионов мелких значений дорого, поэтому их передают пачками.

## 12. Вопросы к защите

### Что такое канал? Почему это инструмент синхронизации, а не только очередь?

Канал — типизированная труба между горутинами: структура `hchan` в куче (мьютекс, кольцевой буфер, очереди ждущих отправителей и получателей), переменная хранит указатель. Это **синхронизация**, потому что операции **блокируют** горутину, пока не готова другая сторона, и модель памяти даёт гарантию happens-before: всё, что отправитель записал до `ch <- v`, видно получателю после `<-ch`. В ping-примере получатель ждал 500 мс без `Sleep`, `WaitGroup` и цикла: ждала сама операция `<-ch`. После её возврата мы **знаем**, что отправитель дошёл до `ch <-`. Небуферизованный канал даже не хранит значение, это чистая точка встречи. Очередь (буфер) — лишь дополнительная возможность.

### Что происходит при send, receive и close для nil, открытого и закрытого канала?

Таблица из раздела 3. Коротко: **nil** — send и receive блокируют навсегда, close паникует. **Открытый** — send ждёт получателя или место, receive ждёт значения, close OK. **Закрытый** — send паникует, receive отдаёт остаток буфера, потом сразу `0, false`, повторный close паникует. Паники — ошибки программиста. «Навсегда» превращается в `fatal error: deadlock`, только если спят все горутины.

### Разница между небуферизованным и буферизованным каналом? Что гарантирует каждый, когда `ch <- v` вернулся?

Небуферизованный — передача из рук в руки: отправка ждёт получателя. Когда `ch <- v` вернулся, **значение уже получено** (получатель дошёл до `<-ch`). Буферизованный — очередь на `cap` мест: отправка ждёт, только если буфер полон. Когда `ch <- v` вернулся, значение **лежит в очереди**, но, может быть, его никто никогда не прочитает. В Task 2: при cap 0 отправки в 300/400/500 мс, при cap 3 все в 0s.

### Кто должен закрывать канал? Что делать, когда отправителей много?

Закрывает **владелец** — тот, кто создал канал и пишет в него, и только он, один раз. Получатель не закрывает: он не знает, будут ли ещё значения, а отправка в закрытый канал — паника. Если отправителей много, не закрывает ни один из них. Отдельная горутина делает `wg.Wait()` и потом `close`. Она обязательно отдельная: иначе `wg.Wait()` до `return` — deadlock. Если отправителей много, а сигнал «стоп» нужен в обратную сторону (от получателя), закрывают **другой** канал — `done`, и отправители выходят по нему.

### Как заканчивается `range` по каналу? Как проверить, закрыт ли канал?

`for v := range ch` заканчивается, когда канал **закрыт и пуст**: буферизованные значения сначала дочитываются. Если канал никто не закроет, `range` висит вечно (утечка или deadlock). Проверка: `v, ok := <-ch`, `ok == false` значит закрыт и пуст. Без чтения проверить нельзя. Неблокирующая проверка — `select { case v, ok := <-ch: …; default: }`, но она тоже читает значение, если оно есть.

### Что делает select, когда готовы несколько кейсов? Когда ни один? С default?

Несколько готовы — выбирается **случайный** (равномерно, порядок в коде не важен; у меня 506/494, 519/481, 484/516). Ни один не готов и нет `default` — горутина ждёт на всех каналах сразу, первый сработавший выигрывает. С `default` — если ни один кейс не готов, сразу выполняется `default`, select не блокируется никогда. Если хоть один кейс готов (например, закрытый канал), `default` не выполняется. `select {}` блокирует навсегда.

### Чем полезен nil-канал внутри select?

Кейс на nil-канале не бывает готов никогда, то есть он **выключен**. Так динамически включают и выключают кейсы, не переписывая `select`. Главный пример — `merge`: когда `a` закрыт, `a = nil`. Без этого закрытый `a` готов всегда (отдаёт `0, false` мгновенно), select постоянно выбирает его, и цикл крутится вхолостую со 100% CPU (у меня 120–190 тыс. пустых итераций). Цикл заканчивается, когда **оба** стали nil. Второй пример: кейс отправки включается, только когда есть что отправлять.

### Что такое backpressure? Три способа реагировать на полную очередь.

Backpressure — давление медленного потребителя назад, на производителя: ограниченная очередь заполняется, и производитель вынужден ждать или отказываться. Ограниченный канал даёт это бесплатно. Реакции:
1. **block** — ждать (`ch <- v`): никто не теряется, производитель замедляется (2.27 с вместо 0.4, задержка ≤ 10 мс);
2. **drop** — `select` с `default`: выбросить, производитель не ждёт (1646 из 2000 потеряно);
3. **wait with timeout** — `select` с таймером: ждать немного, потом ошибка (`ErrQueueFull` → HTTP 503).

### Почему «очень большой буфер» — не решение для медленного потребителя?

Буфер не ускоряет потребителя, он только прячет перегрузку. Задержка растёт вместе с очередью (1.89 с ожидания в эксперименте: пользователь уже ушёл, а работа всё равно делается). При бесконечном потоке очередь растёт без предела, потом OOM, и страдают все. Никто не получает сигнала «притормози». Большой буфер ещё и стоит памяти всегда (Task 7: 80 КБ на канал против 1 КБ). Буфер нужен для **всплесков**. Постоянную разницу скоростей решают ускорением потребителя или ограничением входа.

## 13. Дополнительные вопросы

**Блокирует ли заблокированная на канале горутина поток ОС?** Нет. Она паркуется (`gopark`), M берёт другую горутину из очереди P. Тысячи ждущих горутин — это тысячи `sudog` в очередях, а не потоки.

**Канал или мьютекс?** Канал — для передачи владения данными и сигналов (конвейеры, пулы, отмена, «готово»). Мьютекс — для защиты общего состояния (кэш, счётчик, map). Счётчик через канал медленнее и запутаннее, чем `atomic` или `Mutex`.

**Что будет, если закрыть канал, на котором ждут отправители?** Все они проснутся с `panic: send on closed channel`.

**Можно ли переоткрыть закрытый канал?** Нет. Нужен новый `make`.

**Зачем `chan struct{}`?** Пустая структура занимает 0 байт. Канал несёт только факт события (`done`, сигнал), а не данные.

**`time.After` в цикле — проблема?** Каждый вызов создаёт новый таймер. До Go 1.23 он жил до срабатывания (утечка памяти в горячем цикле). С 1.23 неостановленный таймер собирает GC, но `NewTimer` + `Stop`/`Reset` всё равно экономнее.

**Что напечатает `fmt.Println(<-ch, <-ch)` для cap 2 с `"a"`, `"b"`?** `a b`: аргументы вычисляются слева направо, канал FIFO. При cap 1 до печати не дойдёт: вторая отправка — deadlock.

**Почему в `wrong` сумма 93?** 93 = 30+31+32, это все значения воркера 3. Последняя запущенная горутина попадает в `runnext` и запускается первой, отправляет всё и закрывает канал, `range` заканчивается. Следующая отправка другого воркера — `send on closed channel`. Иногда `close of closed channel`.

**Как сделать так, чтобы `Same` из Tour не тёк?** Канал `done` + `defer close(done)` в `Same`, а в `Walk` каждая отправка через `select` с `<-done`. В версии без `done` было +2000 горутин на 1000 вызовов для разных деревьев, с `done` — 0.

**Почему с `GOMAXPROCS=1` пинг-понг быстрее?** Передача мяча — это переключение горутин на одном потоке, без пробуждения другого ядра и переноса кэш-линии канала: 140 нс против 175 нс на удар.

## 14. Шпаргалка

- Канал = `*hchan`: lock + кольцевой буфер + `sendq`/`recvq`. Нулевое значение — nil, нужен `make`.
- **nil:** send/recv — навсегда, close — panic. **closed:** send — panic, recv — остаток, потом `0,false` сразу, close — panic.
- Unbuffered: «получено». Buffered: «в очереди». Отправка `k` ждёт, если `k > cap` и никто не читает.
- Буфер выбирают по причине (1 результат, N воркеров, всплески), не «1000 на всякий случай». Буфер не лечит deadlock.
- Закрывает **владелец** (кто создал и пишет), один раз. Много писателей → closer-горутина с `wg.Wait()`. Читатели не закрывают.
- `range ch` до закрытия **и** опустошения. `v, ok := <-ch` — проверка.
- `select`: случайный среди готовых, ждёт без `default`, не ждёт с `default`, nil-кейс выключен.
- Закрытый `done` (или `ctx.Done()`) будит **всех**. Каждая потенциально вечная операция — в `select` с `<-done`.
- Таймаут в `select` останавливает ожидание, а не работу. Буфер = числу отправок или отмена.
- Полная очередь: **block, drop, wait+timeout → 503**. Никогда неограниченная очередь.
- Канал ~20–80 нс на операцию. Много данных — пачками.
