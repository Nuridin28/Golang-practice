## 1. Строки, байты, руны — `task1_strings.go`

### Что такое `string`

`string` в Go — неизменяемый (immutable) слайс байт в кодировке UTF-8. Изменить строку после создания нельзя — любая "модификация" на самом деле создаёт новую строку.

`StringBasics()` показывает главную ловушку:

```go
s := "Hello, 世界"
len(s)                        // 13 — количество БАЙТ
utf8.RuneCountInString(s)     // 9  — количество СИМВОЛОВ (рун)
```

`len()` всегда считает байты. Для ASCII байт == символ, поэтому разница незаметна, пока не появляется не-ASCII текст. Чтобы посчитать реальные символы — нужен `unicode/utf8.RuneCountInString`.

### `byte` vs `rune`

- `byte` = `uint8` — один байт.
- `rune` = `int32` — один Unicode code point (символ).

Один символ в UTF-8 занимает от 1 до 4 байт. `'a'` — 1 байт, `'ê'` — 2 байта, `'世'` — 3 байта.

### Почему `s[i]` — это ловушка

`IterationDemo()`:

```go
s := "hêllo"
for i := 0; i < len(s); i++ {
    fmt.Printf("  position %d: %c\n", i, s[i])
}
```

`s[i]` — это индексация по **байтовому** слайсу, она возвращает `byte`, а не символ. `ê` занимает 2 байта, поэтому вывод "ломается": на месте `ê` печатаются мусорные символы (`Ã`, `ª`), а нумерация после него съезжает.

Правильный способ — `for i, r := range s`: `range` сам декодирует UTF-8 на лету и отдаёт `(байтовое_смещение, rune)`. Именно поэтому во втором цикле `IterationDemo()` индексы идут `0, 1, 3, 4, 5` (не `0,1,2,3,4`) — после `ê` смещение прыгает на 2, потому что руна заняла 2 байта.

### Как получить N-ю руну строки — `SecondRuneDemo()`

Два способа:

```go
runes := []rune(s)       // конвертирует ВСЮ строку в []rune (аллокация + полное декодирование)
runes[1]
```

```go
_, size := utf8.DecodeRuneInString(s)     // декодируем первую руну, узнаём её размер в байтах
second, _ := utf8.DecodeRuneInString(s[size:]) // декодируем следующую с этого смещения
```

`[]rune(s)` проще, но платит за удобство: аллоцирует новый слайс и декодирует всю строку сразу, даже если нужен один символ. `utf8.DecodeRuneInString` декодирует только то, что нужно, без лишней аллокации — актуально, если строка большая, а нужен один символ.

### Trim-функции — `TrimDemo()`

Ключевая путаница в задании: `TrimRight`/`TrimLeft` и `TrimPrefix`/`TrimSuffix` выглядят похоже, но работают принципиально по-разному.

```go
strings.TrimRight("123oxo", "xo")   // "123"  — убирает СИМВОЛЫ ИЗ НАБОРА с конца, пока не встретит символ вне набора
strings.TrimSuffix("123oxo", "xo")  // "123o" — убирает ТОЧНУЮ ПОДСТРОКУ "xo" один раз, если строка ей заканчивается
```

- `TrimRight(s, cutset)` — второй аргумент это **набор символов** (cutset), а не подстрока. Убирает с конца все символы, которые входят в этот набор, пока не встретит символ, которого там нет. Поэтому `"123oxo"` с cutset `"xo"` теряет и `o`, и `x`, и снова `o` — три символа подряд, все входят в набор `{x, o}`.
- `TrimSuffix(s, suffix)` — второй аргумент это **точная подстрока**. Убирается ровно одно совпадение целиком, с конца.

То же для `TrimLeft` (набор символов слева) и `TrimPrefix` (точная подстрока слева) — в демо `TrimPrefix("xoxo123", "xo")` даёт `"xo123"`, потому что убирает только первое вхождение `"xo"`, а не всё, что состоит из `x`/`o`.

**Правило:** если нужно убрать конкретный суффикс/префикс — всегда `TrimSuffix`/`TrimPrefix`. `TrimLeft`/`TrimRight` — только когда реально нужно "срезать все символы из набора".

### Конкатенация строк — `BuilderGrowDemo()`

Наивный вариант:

```go
s := ""
for _, v := range values {
    s += v   // на КАЖДОЙ итерации: новая аллокация + копирование всего накопленного
}
```

Каждый `+=` создаёт новую строку, потому что строки неизменяемы — старую нельзя дописать "на месте". При N конкатенациях это O(n²) по времени и памяти.

Решение — `strings.Builder`:

```go
var sb strings.Builder
sb.Grow(totalLength)   // резервируем память под результат ОДИН раз заранее
for _, v := range values {
    sb.WriteString(v)  // пишет в общий буфер, без новых строк на каждой итерации
}
sb.String()             // без копирования (unsafe cast) отдаёт результат
```

`Grow(n)` — если известна итоговая длина, она резервирует буфер сразу нужного размера, чтобы `Builder` не переаллоцировал буфер несколько раз по мере роста (как это делает `append` для слайсов без указанной capacity).

## 2. `[]byte` ↔ `string` — `task2_payload.go`

### Почему конвертации не бесплатны

`string` неизменяем, `[]byte` — изменяем. Они не могут "шарить" один и тот же кусок памяти безопасно, поэтому **любая** конвертация `string(b)` или `[]byte(s)` — это копирование всех байт в новый аллоцированный блок памяти. Это O(n) по времени и +1 аллокация на каждый вызов.

### `processPayload` (оригинал, "плохой" вариант)

```go
func processPayload(data []byte) string {
    trimmed := string(bytes.TrimSpace(data))       // аллокация #1: []byte -> string
    clean := strings.ReplaceAll(trimmed, "\r", "")  // аллокация #2: новая строка без \r
    return clean
}
```

`bytes.TrimSpace` сам по себе ничего не аллоцирует — просто возвращает подрезанный **под-слайс** того же массива. Но сразу после этого `string(...)` копирует эти байты в новую строку — только чтобы её тут же передать в `strings.ReplaceAll`, которая аллоцирует ещё раз. Итого: 2 аллокации, при этом первая — временная, от неё сразу избавляемся.

### `processPayloadOptimized` (byte-ориентированная версия)

```go
func processPayloadOptimized(data []byte) string {
    trimmed := bytes.TrimSpace(data)   // без аллокации — под-слайс

    var sb strings.Builder
    sb.Grow(len(trimmed))
    for _, b := range trimmed {
        if b == '\r' {
            continue
        }
        sb.WriteByte(b)
    }
    return sb.String()   // единственная аллокация — сразу финальный результат
}
```

Идея: не конвертировать в промежуточную строку вообще. Работаем с `[]byte` до самого конца, фильтруем `\r` за один проход прямо в заранее засайженный (`Grow`) `strings.Builder`, и только в конце получаем строку — причём `Builder.String()` не копирует память повторно (unsafe-приведение внутреннего буфера).

### Бенчмарк — `task2_payload_test.go`

```
BenchmarkProcessPayload/Original-10     38.41 ns/op   96 B/op   2 allocs/op
BenchmarkProcessPayload/Optimized-10    96.95 ns/op   48 B/op   1 allocs/op
```

Что видно:
- **allocs/op упал с 2 до 1** — убрали лишнюю промежуточную аллокацию `string(bytes.TrimSpace(...))`.
- **B/op упал с 96 до 48** — меньше памяти выделяется суммарно.
- **ns/op при этом выше** (96.95 vs 38.41) — это честный компромисс: `bytes.TrimSpace` + `strings.ReplaceAll` внутри реализованы через оптимизированный `memmove`/поиск подстроки на уровне рантайма, а наш ручной цикл `for _, b := range trimmed { sb.WriteByte(b) }` вызывает `WriteByte` на каждый байт по отдельности, и это медленнее по чистому времени, хоть и экономит аллокации.

Вывод для защиты: "меньше аллокаций" не всегда значит "быстрее" — аллокации бьют по GC-нагрузке и памяти, а не обязательно по CPU-времени одного вызова. В реальном коде выбор зависит от того, что важнее: throughput аллокатора/GC при большом количестве вызовов, или ns одного вызова.

## 3. Maps — `task3_maps.go`, `task4_inventory.go`

### Как map устроена внутри

Map — это хеш-таблица. При операции (чтение/запись/удаление) Go:
1. Считает хеш ключа.
2. По хешу находит нужный **бакет** (bucket).
3. Внутри бакета ищет нужный слот по control-словам (в современной реализации Go — на основе Swiss Tables).

В среднем все операции — O(1) благодаря хорошей хеш-функции и эффективному пробингу. В худшем случае (много коллизий, либо момент роста карты) — дороже.

### Рост map (rehash)

Карта растёт, когда:
- **load factor** (в среднем элементов на бакет) превышает порог (~6.5, внутренний параметр);
- или бакет переполнен (**bucket overflow**, больше 8 элементов в бакете).

При росте **все ключи перераспределяются** по новым бакетам — вставка в этот момент может стоить O(n) вместо обычного O(1).

### Зачем `make(map[K]V, N)`

Если заранее известно примерное число элементов — `make(map[string]int, 1_000_000)` резервирует нужное число бакетов сразу, вместо того чтобы map росла и перехешировалась много раз по мере наполнения через обычные присваивания. Дешевле по суммарному времени вставки большого числа элементов.

### Базовые операции — `MapOperationsDemo()`

```go
m := map[string]int{"one": 1, "two": 2}
m["one"]          // read
m["two"] = 20      // update
delete(m, "one")   // delete
```

### Проверка наличия ключа — двузначное присваивание

```go
v, ok := m[key]
```

Если ключа нет, `m[key]` в одиночном виде вернёт **нулевое значение** типа (для `int` — `0`), и это неотличимо от ситуации "ключ есть, но значение 0". `ok` (`bool`) решает эту проблему — `true`, если ключ реально присутствует в карте.

Именно это демонстрирует `ScoresTask()`:

```go
scores := map[string]int{"Alice": 90, "Bob": 0}

_, ok := scores["Bob"]      // ok == true  — Bob в карте, просто со значением 0
_, ok = scores["Charlie"]   // ok == false — Charlie реально отсутствует
```

Без `ok` было бы невозможно понять, что `Bob` сдал экзамен на 0 баллов, а не "не найден".

### `InventoryTask()` — CRUD на map

```go
inventory := map[string]int{"apples": 10, "bananas": 5}

inventory["apples"]          // read
inventory["bananas"] = 12    // update
inventory["oranges"] = 8     // insert (новый ключ)
delete(inventory, "apples")  // delete
```

Insert и update в Go — это **один и тот же синтаксис** (`m[key] = value`): если ключа не было — он создаётся, если был — перезаписывается. Разделения на "insert" и "update" на уровне языка нет, это чисто логическое разделение из задания.
