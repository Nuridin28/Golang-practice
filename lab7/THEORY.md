## 1. Concurrency vs parallelism

### 1.1 Определения

> «Concurrency is about **dealing** with lots of things at once. Parallelism is about **doing** lots of things at once.» — Rob Pike

- **Concurrency (конкурентность)** — свойство **структуры** программы. Программа состоит из независимых задач, которые могут продвигаться, не дожидаясь друг друга. Это про то, как программа *написана*.
- **Parallelism (параллелизм)** — свойство **исполнения**. Несколько задач в один и тот же момент выполняются на разных ядрах. Это про то, как программа *выполняется*.

Concurrency даёт **возможность** параллелизма, но не гарантирует его. Конкурентная программа на одном ядре работает без параллелизма: задачи по очереди делят процессор. Та же программа без изменений на 8 ядрах становится параллельной. В докладе Пайка это гоферы, которые сжигают книги: сначала задачу правильно **разбивают** на независимые части (конкурентная структура), а потом эти части можно раздать нескольким гоферам (параллельное исполнение).

### 1.2 Два вида работы

| | CPU-bound | I/O-bound |
|---|---|---|
| На что уходит время | на вычисления | на ожидание: база, сеть, диск, `time.Sleep` |
| Примеры | простые числа, хеши, ресайз картинок, bcrypt, сжатие | HTTP-запрос, SQL-запрос, чтение файла |
| Что ускоряет | **больше свободных ядер** | **больше горутин**: ждущая горутина не тратит CPU |
| Что даёт `GOMAXPROCS=1` | никакого ускорения от горутин | ускорение такое же, как на многих ядрах |

**I/O-bound нужна только concurrency:** 1000 горутин ждут одновременно, и общее время равно самому долгому ожиданию, а не сумме ожиданий. **CPU-bound нужен parallelism:** работа не уменьшается, её можно только раздать нескольким ядрам.

### 1.3 Почему ускорение никогда не идеальное

Даже на N ядрах CPU-работа ускоряется меньше чем в N раз:

1. **Ядер меньше, чем горутин.** Лишние горутины стоят в очереди.
2. **Дисбаланс работы.** `wg.Wait()` ждёт **самую медленную** горутину, а остальные ядра к концу простаивают. В нашей лабе куски одинаковой длины, но большие числа проверять дороже (Task 1: 157 мс против 256 мс).
3. **Накладные расходы**: создание горутин, синхронизация, переключения (Task 7: `parts=200000`).
4. **Неравные ядра.** У M4 4 быстрых и 6 медленных ядер.
5. **Закон Амдала.** Если долю `p` работы можно распараллелить, а `1−p` нельзя, то ускорение ≤ `1 / ((1−p) + p/N)`. Например, при 10% последовательной работы больше 10× не получить никогда.

## 2. Горутины

### 2.1 Что это

**Горутина** — функция, которая выполняется конкурентно с остальной программой. Горутинами управляет **рантайм Go**, а не операционная система. Запуск — ключевое слово `go` перед вызовом функции:

```go
go doSomething(x)        // именованная функция
go func() { ... }()      // анонимная функция (замыкание)
go obj.Method(y)         // метод
```

`main` — тоже горутина (в профилях её видно как `goroutine 1`).

### 2.2 Аргументы вычисляются сразу

Спецификация: значение функции и её аргументы вычисляются **в вызывающей горутине, в момент выполнения `go`**. Сама функция запускается позже.

```go
x := 1
go show(x) // x вычисляется СЕЙЧАС
x = 2
// go show got 1
// x is 2
```

Замыкание `go func() { show(x) }()` работает иначе: оно захватывает **переменную**, и горутина прочитает то значение, которое будет в `x` в момент выполнения. Без синхронизации это ещё и data race.

### 2.3 Результат горутины

Значение, которое возвращает функция, запущенная через `go`, **отбрасывается**. Результат передают:
- через канал (`ch <- v`);
- через свой элемент слайса (`results[i] = v`), который читают после `wg.Wait()`;
- через общую переменную под `mutex`/`atomic`.

### 2.4 `main` не ждёт

Когда `main` возвращается (или вызывается `os.Exit`), **программа завершается**. Все остальные горутины останавливаются мгновенно, где бы они ни были. Их `defer` **не выполняются**, буферы не сбрасываются. Поэтому `main` должна ждать явно: `WaitGroup`, каналы, `errgroup`.

### 2.5 У горутины нет ID и её нельзя убить

- У горутины **нет доступного ID**. Это сделано специально, чтобы не появлялось goroutine-local storage: данные передают явно, через параметры и `context`.
- **Убить горутину снаружи нельзя.** Горутина заканчивается только когда:
  1. её функция вернулась;
  2. она сама вызвала `runtime.Goexit()` (её `defer` при этом выполняются);
  3. завершился весь процесс (`main` вернулась, паника, `os.Exit`).

  Остановить горутину можно только **попросив**: закрыть канал, отменить `context`. Горутина должна сама проверять этот сигнал.

### 2.6 Порядок выполнения не определён

Спецификация **ничего** не обещает о том, в каком порядке выполняются горутины. Сегодняшний порядок — это деталь реализации планировщика (раздел 7.6, Bonus). Если порядок важен, его задают синхронизацией.

## 3. `sync.WaitGroup`

### 3.1 API

`WaitGroup` — это счётчик незавершённых задач:

| Метод | Что делает |
|---|---|
| `wg.Add(n)` | счётчик += n |
| `wg.Done()` | счётчик −= 1 (это `Add(-1)`) |
| `wg.Wait()` | блокируется, пока счётчик не станет 0 |
| `wg.Go(f)` (Go 1.25+) | `Add(1)` + `go func() { defer Done(); f() }()` |

```go
var wg sync.WaitGroup
for i := 1; i <= 5; i++ {
    wg.Add(1)            // 1. посчитать горутину ДО запуска
    go func() {
        defer wg.Done()  // 2. «я закончила» — defer, чтобы сработало и при раннем return
        work(i)
    }()
}
wg.Wait()                // 3. ждать, пока счётчик не станет 0
```

### 3.2 Правила (и что будет, если их нарушить)

1. **`Add` — до `go`, в родительской горутине.** Если `Add` стоит внутри горутины, `Wait` может выполниться раньше и увидеть 0 (Task 2.2). `go vet` (анализатор `waitgroup`, Go 1.25+): `WaitGroup.Add called from inside new goroutine`.
2. **`Done` вызывается ровно один раз на каждый `Add(1)`.** Лишний `Done`:
   ```
   panic: sync: negative WaitGroup counter
   ```
   Недостающий `Done` означает, что `Wait` ждёт вечно. Если больше никого нет:
   ```
   fatal error: all goroutines are asleep - deadlock!
   goroutine 1 [sync.WaitGroup.Wait]:
   ```
3. **`WaitGroup` нельзя копировать.** Копия — это другой счётчик. `go worker(wg)` по значению: `Done` уменьшает копию, а `Wait` ждёт вечно. Передают `*sync.WaitGroup` или захватывают замыканием. `go vet` (copylocks):
   ```
   worker passes lock by value: sync.WaitGroup contains sync.noCopy
   ```
4. Переиспользовать `WaitGroup` можно только после того, как предыдущий `Wait` вернулся.

### 3.3 Почему после `Wait` можно читать результаты без мьютекса

Модель памяти Go: вызов `Done`, который уменьшил счётчик до нуля, **синхронизирован с** возвратом `Wait`, который он разблокировал (*happens before*). Значит, всё, что горутина записала **до** `Done` (например, `results[i] = ...`), гарантированно видно `main` **после** `Wait`.

### 3.4 Переменная цикла с Go 1.22

С Go 1.22 (если в `go.mod` стоит `go 1.22` или выше) у **каждой итерации своя** `i`. Замыкание `go func() { use(i) }()` видит правильное значение. До 1.22 переменная была одна на весь цикл, и все горутины часто видели последнее значение. В нашем `go.mod` стоит `go 1.25`.

### 3.5 Родственник: `errgroup`

`golang.org/x/sync/errgroup` — это WaitGroup плюс ошибки: `g.Go(func() error)`, `g.Wait()` возвращает первую ошибку, а `errgroup.WithContext` отменяет `ctx` при первой ошибке. В лабе не нужен, но про него могут спросить.

## 4. Data race и модель памяти

### 4.1 Определение

**Data race** — две горутины обращаются к **одной ячейке памяти одновременно**, хотя бы одна из них **пишет**, и между обращениями **нет синхронизации** (нет отношения happens-before). Атомарные операции из `sync/atomic` гонкой не считаются.

### 4.2 Почему `counter++` теряет инкременты

`counter++` — это **три шага**: прочитать → прибавить → записать.

```
горутина A          горутина B          counter
read  (5)                               5
                    read  (5)           5
add   → 6                               5
                    add   → 6           5
write 6                                 6
                    write 6             6   ← два инкремента, а прибавилось 1
```

Task 2.2: `counter: 991, 991, 984` вместо 1000.

### 4.3 Последствия гонки хуже, чем «немного не то число»

- **Разорванные значения.** `string`, слайс и интерфейс занимают несколько машинных слов. Если читатель увидит указатель от нового значения и длину от старого, программа падает или читает чужую память.
- **Компилятор и процессор** вправе переставлять и кэшировать обращения, если не видят синхронизации. Цикл `for !done {}` может никогда не увидеть `done = true`.
- **Map**: одновременная запись — это **fatal error**, а не паника. `recover` её **не ловит**:
  ```
  fatal error: concurrent map writes
  ```
- «Безобидных» гонок в Go не бывает: программа с гонкой некорректна по определению.

### 4.4 Что даёт happens-before (что синхронизирует)

| Операция | Гарантия |
|---|---|
| `go f()` | всё до `go` видно внутри `f` |
| отправка в канал | происходит до того, как соответствующее получение завершится |
| `close(ch)` | происходит до получения нулевого значения из закрытого канала |
| небуферизованный канал | получение происходит до того, как отправка завершится |
| `mu.Unlock()` | происходит до следующего `mu.Lock()` |
| `wg.Done()` | происходит до возврата `wg.Wait()` |
| `once.Do(f)` | `f` завершилась до возврата любого `Do` |
| `atomic` | атомарные операции упорядочены между собой (sequentially consistent) |

**Выход** горутины ни с чем не синхронизирован. Без `WaitGroup`/канала нельзя узнать, что она закончилась, и нельзя безопасно читать то, что она записала.

### 4.5 Race detector

```
go run -race .     go test -race ./...     go build -race
```
- Основан на ThreadSanitizer. Во время выполнения отслеживает каждое обращение к памяти и отношения happens-before.
- Находит гонку и печатает **оба стека**: кто читал/писал и где была создана каждая горутина. При найденной гонке код выхода **66**.
- Стоимость: программа в несколько раз медленнее и ест в несколько раз больше памяти, поэтому `-race` включают в тестах и CI, а не в продакшене.
- **Находит только гонки, которые реально произошли в этом запуске.** Нет гонки в отчёте — не значит, что её нет. Нужны тесты, которые нагружают конкурентный код.
- Под `-race` рантайм ещё и **перемешивает планировщик** (Bonus: 16 разных порядков из 1000), чтобы вскрывать код, который полагается на порядок.
- Детектор проверяет **синхронизацию, а не реальную одновременность.** Запись в общий `strings.Builder` из 5 горутин при `GOMAXPROCS(1)` он тоже назвал гонкой. Физически они не пересекались, но порядок ничем не гарантирован.

### 4.6 Четыре способа исправить

| Способ | Пример | Когда |
|---|---|---|
| `sync/atomic` | `var c atomic.Int64; c.Add(1)` | один счётчик или флаг; быстро, без блокировок |
| `sync.Mutex` | `mu.Lock(); c++; mu.Unlock()` | несколько полей нужно менять согласованно |
| каналы | передавать данные, а не делить их | «Don't communicate by sharing memory; share memory by communicating» |
| **confinement** (у каждого свои данные) | `results[i] = ...` | данные можно разделить: синхронизация не нужна вообще |

Разные элементы слайса — разные ячейки памяти, поэтому `results[i]` из разных горутин — **не гонка**. (Соседние элементы могут лежать в одной кэш-линии, и тогда возможна потеря производительности, *false sharing*, но это не про корректность. При одной записи на горутину это незаметно.)

## 5. Паника в горутине

### 5.1 Паника, которую никто не поймал, убивает всю программу

Паника раскручивает стек **той горутины, где она случилась**. Если она дошла до верха стека горутины и её никто не поймал, **весь процесс** падает с кодом выхода 2, даже если `main` ни при чём.

```
panic: assignment to entry in nil map
goroutine 5 [running]:
main.panicInGoroutine.func2()
created by main.panicInGoroutine in goroutine 1
```

### 5.2 Правила `recover`

1. `recover` работает только внутри **отложенной (`defer`) функции**.
2. Её нужно вызвать **непосредственно** в этой отложенной функции. `defer recover()` **не работает**: проверено, паника проходит дальше.
3. `recover` ловит панику только **своей горутины**. `defer recover` в `main` не видит паники в других горутинах: у каждой горутины свой стек и своя цепочка `defer`.

### 5.3 Где должен стоять `defer`

Внутри функции самой горутины, **первой строкой**, до кода, который может паниковать:

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Println("recovered:", r)
        }
    }()
    riskyWork()
}()
```
Обычно это оборачивают в helper `safeGo(f)`. Так делает `net/http`: паника в обработчике одного запроса логируется (`http: panic serving ...`) и не роняет сервер.

### 5.4 Что `recover` не ловит (fatal errors)

`concurrent map writes`, `all goroutines are asleep - deadlock!`, нехватка памяти, переполнение стека (`goroutine stack exceeds 1000000000-byte limit`), превышение лимита потоков. Это `fatal error`, а не `panic`, и процесс завершается без шансов.

## 6. Сколько стоит горутина

### 6.1 Стек горутины

- Стартовый размер **2 KB** (Task 3: ровно 2.0 KB на горутину).
- **Растёт по необходимости.** В прологе каждой функции (кроме `nosplit`) компилятор вставляет проверку «хватит ли стека» (SP сравнивается с `g.stackguard0`). Если не хватает, вызывается `morestack`: выделяется стек **в 2 раза больше**, старый копируется, указатели на стек исправляются (contiguous / copying stacks, Week 7).
- Во время GC стек может **уменьшиться** (если используется меньше 1/4).
- Максимум — 1 GB на 64-битных системах, дальше `fatal error: stack overflow`.
- Та же проверка в прологе используется для **кооперативного вытеснения** (раздел 8).

### 6.2 Горутина vs поток ОС

| | Горутина | Поток ОС |
|---|---|---|
| Стек | 2 KB, растёт и уменьшается | 1–8 MB, фиксированный (резервируется сразу) |
| Кто создаёт и планирует | рантайм Go, в user space | ядро ОС |
| Создание | ~0.2–1 мкс, без syscall | syscall, десятки мкс |
| Переключение | дёшево: сохранить несколько регистров (PC, SP, BP) | дорого: переход в ядро, полный набор регистров, ~мкс |
| Сколько — это «много» | сотни тысяч, миллионы | тысячи |

Почему переключение горутин дешёвое: оно происходит в **известных точках** (вызов функции, блокировка на канале). Компилятор там уже сохранил живые регистры, поэтому рантайму почти нечего сохранять. Ядро прерывает поток в любой точке и вынуждено сохранять всё.

### 6.3 Наши цифры (Task 3)

```
100 000 горутин:   стек 195 MB = 2.0 KB/шт, прочее ~700 B/шт (g, sudog, замыкание), старт ~0.95 мкс/шт
1 000 000 горутин: стек 1953 MB, прочее 669 MB — всего ~2.6 GB
BenchmarkGoroutineStartStop   225 ns/op   40 B/op   2 allocs/op
BenchmarkFuncCall             0.70 ns/op
```

### 6.4 Когда горутина не окупается

Если работа в горутине сопоставима с её стоимостью (~0.2 мкс + 2.7 KB + аллокации) или меньше, горутина только мешает. Task 7: `parts=200000` — 19 нс работы на горутину, и всё стало в 7–19 раз медленнее. Правила:
- группировать работу **в куски**, хотя бы по десяткам–сотням микросекунд на горутину;
- при огромном числе задач **ограничивать** число одновременных горутин: worker pool или семафор через буферизованный канал `sem := make(chan struct{}, N)`.

## 7. Планировщик: G, M, P

### 7.1 Зачем свой планировщик

Go использует модель **M:N**: много горутин (N) работают поверх нескольких потоков ОС (M). Потоки дорогие (раздел 6.2), а рантайм **знает**, когда горутина блокируется (канал, мьютекс, сеть, sleep), и может сразу подставить другую, не трогая ядро.

### 7.2 Три сущности

| | Что это | Подробности |
|---|---|---|
| **G** — goroutine | функция + стек + состояние | состояния: runnable (готова), running, waiting (ждёт канал/мьютекс/таймер/сеть), syscall, dead (переиспользуется) |
| **M** — machine | настоящий поток ОС | исполняет код. Чтобы исполнять **Go-код**, M обязан держать P. M в syscall может быть без P |
| **P** — processor | «разрешение выполнять Go-код» + ресурсы | локальная очередь G (кольцо на **256**) + слот **`runnext`**, кэш памяти `mcache`, таймеры. P ровно **`GOMAXPROCS`** штук |

Зачем нужен P, почему не просто M: когда M уходит в syscall, его P (очередь, кэш памяти, таймеры) **передают** другому M, и работа продолжается. Ресурсы привязаны к P, а не к потоку.

### 7.3 Очереди и что делает `go f()`

```
           глобальная очередь (общая, под замком)
                ↑ переполнение / вытесненные G
   P0: runnext=[G9]  local=[G3 G4 G5 ...]      P1: runnext=[ ]  local=[G7]
   M0 ────────── исполняет G1                  M1 ────────── исполняет G2
```

`go f()` (функция рантайма `newproc`):
1. Создаёт G (или берёт мёртвую из free list) со стеком 2 KB.
2. Кладёт её **в `runnext` текущего P**. Если там была другая G, та уходит **в хвост** локальной очереди.
3. Если локальная очередь полна (256), **половина** очереди + новая G переносятся в глобальную очередь.
4. Если есть свободный P, будит M (`wakep`), чтобы тот начал искать работу.

### 7.4 Где M ищет следующую G (`schedule` → `findRunnable`)

1. Раз в **61** тик планировщика сначала смотрит в **глобальную** очередь, чтобы та не голодала.
2. **`runnext`**, затем локальная очередь P (FIFO).
3. Глобальная очередь.
4. **Netpoller**: горутины, у которых готов сетевой ввод-вывод.
5. **Work stealing**: до 4 проходов по другим P в случайном порядке, у найденного **крадёт половину** локальной очереди. `runnext` чужого P крадут в последнюю очередь (после ~3 мкс ожидания).
6. Ничего не нашёл — отдаёт P, и M засыпает.

### 7.5 Work stealing

Нет центрального распределителя: каждый P работает со своей очередью без блокировок, а **пустой P сам ищет работу** у соседей. Поэтому все ядра заняты, даже если горутины создаёт одна горутина на одном P (Task 7: `parts=8` и `parts=1000` балансируются сами, быстрые ядра берут больше кусков).

**Spinning M** — поток, который не уснул, а **активно ищет работу** (крутится в шагах 3–5), чтобы мгновенно подхватить новую G. Их число ограничено: не больше половины занятых P, иначе они жгли бы CPU впустую.

### 7.6 `runnext` и загадка «worker 5 первый»

```go
for i := 1; i <= 5; i++ { wg.Add(1); go worker(i) }
wg.Wait()
```
```
go w1: runnext=1  queue=[]
go w2: runnext=2  queue=[1]
go w3: runnext=3  queue=[1 2]
go w4: runnext=4  queue=[1 2 3]
go w5: runnext=5  queue=[1 2 3 4]
wg.Wait() → main паркуется → schedule(): сначала runnext (5), потом очередь: 1 2 3 4
```
Зачем `runnext`: только что созданная или разбуженная G обычно работает с теми же данными, что и её создатель (схема producer → consumer, данные ещё в кэше). Её выгодно запустить следующей, причём в **оставшийся квант** создателя.

- `GOMAXPROCS=1`: всегда `5 1 2 3 4` (наши 10/10 и 1000/1000).
- 10 P: `wakep` будит другие P, они крадут workers 1–4 и запускают их параллельно, пока `main` ещё создаёт остальных. Порядок случайный, 5 первый примерно в половине запусков.
- Под `-race` планировщик специально перемешивается.

### 7.7 Что происходит, когда G блокируется

| Ситуация | Что делает рантайм | Новый поток? |
|---|---|---|
| канал, мьютекс, `WaitGroup`, `select` | G **паркуется** (`gopark`): состояние waiting, G записана в очередь ожидания канала/семафора. M берёт следующую G | нет |
| `time.Sleep`, таймер | G паркуется, таймер в куче таймеров P. Когда сработает, G снова runnable | нет |
| сеть (`net.Conn`) | неблокирующий сокет + **netpoller** (kqueue на macOS, epoll на Linux). G паркуется, пока ОС не скажет, что данные готовы | нет |
| **блокирующий syscall** (файлы, `select(2)`, …), **cgo** | G уходит в ядро **вместе с M**. P отдают другому M (раздел 9) | **да**, если свободных M нет |

### 7.8 `sysmon` — фоновый надсмотрщик

Отдельный M, который работает **без P** и просыпается раз в 20 мкс … 10 мс. Его задачи:
- **забирать P у M, застрявших в syscall** дольше ~20 мкс, и отдавать P другому M;
- **вытеснять G, которая работает дольше 10 мс** (раздел 8);
- опрашивать netpoller, если его никто не опрашивал больше 10 мс;
- запускать GC, если его не было больше 2 минут.

### 7.9 `GOMAXPROCS`

```go
runtime.NumCPU()        // сколько логических ядер доступно процессу
runtime.GOMAXPROCS(0)   // текущее значение (0 = только прочитать)
runtime.GOMAXPROCS(n)   // установить (останавливает мир; почти никогда не нужно)
```
Переменная окружения: `GOMAXPROCS=2 ./prog`.

- `GOMAXPROCS` = **число P** = сколько горутин **одновременно выполняют Go-код**.
- По умолчанию равно числу ядер. Больше ядер ставить бессмысленно для CPU-работы (Task 1: 15, 20 и 40 горутин не быстрее 10).
- **Не** ограничивает число потоков: M в syscall не держат P (Task 4: 102 потока при `GOMAXPROCS=2`).
- **Go 1.25, container-aware:** на Linux по умолчанию учитывается **CPU-лимит cgroup** (Docker `--cpus`, Kubernetes `limits.cpu`; *requests* не учитываются). Значение **обновляется**, если лимит или число ядер меняются. Отключается, если `GOMAXPROCS` задан вручную, или через `GODEBUG=containermaxprocs=0` / `updatemaxprocs=0`. Работает только при `go 1.25+` в `go.mod`.
  - Зачем это нужно: в контейнере с лимитом 2 CPU на 64-ядерной машине раньше было `GOMAXPROCS=64`. 64 потока выедали квоту CFS за малую долю периода, после чего ядро **замораживало** процесс до конца периода, и появлялись скачки задержек. Раньше эту проблему решала библиотека `uber-go/automaxprocs`.

### 7.10 `GODEBUG=schedtrace`

```
GOMAXPROCS=2 GODEBUG=schedtrace=1000 ./sched busy        # строка раз в 1000 мс
GODEBUG=schedtrace=1000,scheddetail=1 ./sched busy        # + состояние каждого P, M, G
```
```
SCHED 1005ms: gomaxprocs=2 idleprocs=0 threads=4 spinningthreads=0 needspinning=1 idlethreads=1 runqueue=3 [ 2 1 ] schedticks=[ 38 43 ]
```

| Поле | Смысл |
|---|---|
| `SCHED 1005ms` | время с начала программы |
| `gomaxprocs` | число P |
| `idleprocs` | P без работы |
| `threads` | всего M (потоков), включая `sysmon` и спящие |
| `spinningthreads` | M, которые активно ищут работу |
| `needspinning` | 1 = работа появилась, а свободного P нет. Флаг просит P, который освободится первым, не засыпать, а искать работу |
| `idlethreads` | спящие M |
| `runqueue` | G в **глобальной** очереди |
| `[ 2 1 ]` | G в **локальных** очередях P0, P1 |
| `schedticks` | сколько раз каждый P выбрал новую G (нагляднее всего видно переключения) |

## 8. Вытеснение (preemption)

### 8.1 Зачем

Без вытеснения горутина, которая долго считает, держит P сколько угодно: другие горутины на этом P голодают, растут задержки, а **GC не может остановить мир** (stop-the-world ждёт, пока все G дойдут до безопасной точки).

### 8.2 Кооперативное вытеснение (было всегда)

Горутина уступает P только в **определённых точках**: блокировка (канал, мьютекс, syscall), `runtime.Gosched()` и **пролог функции**. Трюк: чтобы попросить G уступить, рантайм записывает в `g.stackguard0` специальное значение `stackPreempt`. Ближайшая проверка стека в прологе функции «проваливается», вызывается `morestack`, а он видит `stackPreempt` и отдаёт P планировщику.

**Проблема:** в цикле **без вызовов функций** (`for {}`, `for i := 0; i < 1e10; i++ { sum += i }`) проверок нет, и горутина не уступит никогда. До Go 1.14 это подвешивало программы и GC.

### 8.3 Асинхронное вытеснение (Go 1.14+)

1. `sysmon` видит, что G работает дольше **10 мс** (`forcePreemptNS`).
2. Ставит флаг вытеснения и **посылает потоку сигнал `SIGURG`**.
3. Обработчик сигнала проверяет, что текущая инструкция — **безопасная точка** (GC сможет точно разобрать стек).
4. Если да, обработчик подменяет контекст так, чтобы поток «вызвал» `asyncPreempt`. Та сохраняет **все** регистры и отдаёт P планировщику. Вытесненная G уходит в **глобальную** очередь.

Почему `SIGURG`: обычные программы его не используют, по умолчанию он ничего не убивает, и отладчики к нему спокойно относятся.

### 8.4 Демо (Task 4.2)

```
$ ./sched preempt                               → main is still alive
$ GODEBUG=asyncpreemptoff=1 ./sched preempt     → висит вечно
```
`GOMAXPROCS(1)`, горутина `for {}` получает единственный P, как только `main` засыпает. С асинхронным вытеснением через ~10 мс её вытесняют, и `main` печатает строку. С `asyncpreemptoff=1` остаётся только кооперативное вытеснение, флаг никто не проверяет, и `main` не получит P никогда.

### 8.5 Квант

Go не делит время на точные кванты. Горутина работает, пока не заблокируется или пока `sysmon` не заметит, что прошло >10 мс (на практике 10–20 мс). Видно в `schedticks`: ~40 переключений в секунду на P.

## 9. Системные вызовы и потоки

### 9.1 Что происходит при блокирующем syscall

1. G вызывает syscall → `entersyscall`: P помечается «в syscall», но **пока остаётся** у M (вдруг вызов быстрый).
2. Если вызов идёт дольше ~20 мкс, `sysmon` **забирает P** (`retake`) и отдаёт его другому M: спящему или **новому**. Тот продолжает выполнять другие G.
3. Syscall завершается → `exitsyscall`: G пытается получить свой P обратно или любой свободный. Не получилось — G идёт в глобальную очередь, а M засыпает (поток **остаётся**, его не уничтожают).

### 9.2 Task 4.3: `time.Sleep` vs `select(2)`

```
start                    threads created so far: 4
100 x time.Sleep         threads created so far: 4      ← G паркуются, потоки не нужны
100 x blocking syscall   threads created so far: 102    ← каждая G держит свой M в ядре
100 x time.Sleep again   threads created so far: 102    ← потоки остались, новых нет
```
На macOS нет `syscall.Nanosleep`, поэтому используется `syscall.Select(0, nil, nil, nil, &tv)`: системный вызов `select(2)` без дескрипторов и с таймаутом, то есть «поспать в ядре». Поток при этом заблокирован целиком.

### 9.3 Что ещё блокирует M

- **Файловый ввод-вывод** (`os.File` на диске). Сотни одновременных чтений с диска — сотни потоков.
- **cgo-вызовы** — ведут себя как syscall.
- `runtime.LockOSThread()` — G привязана к своему M.

Сеть потоки **не** блокирует: она идёт через netpoller.

### 9.4 Лимит потоков

`debug.SetMaxThreads` — по умолчанию **10 000**. При превышении процесс падает (`fatal error`). Это защита от бесконечного роста потоков, если, например, 20 000 горутин одновременно ушли в блокирующий syscall.

## 10. Каналы, select, context — минимум для лабы

### 10.1 Каналы

```go
ch := make(chan int)      // небуферизованный: отправка ждёт получателя (рандеву)
ch := make(chan int, 1)   // буфер 1: отправка не блокируется, пока в буфере есть место
```

| Операция | nil-канал | открытый | закрытый |
|---|---|---|---|
| `ch <- v` | блокируется навсегда | ждёт получателя / место в буфере | **panic: send on closed channel** |
| `<-ch` | блокируется навсегда | ждёт значение | сразу: нулевое значение, `ok == false` |
| `close(ch)` | **panic** | закрывает | **panic** |

`close` будит **всех** ожидающих получателей сразу. Так удобно рассылать сигнал «стоп» (Task 3: `close(stop)` будит 100 000 горутин).

### 10.2 `select`

```go
select {
case v := <-ch:        // что первое готово, то и выполнится
case <-time.After(d):  // таймаут
case <-ctx.Done():     // отмена
default:               // если ничего не готово — не ждать
}
```
- Если готово несколько веток, выбирается **случайная**.
- `select {}` блокируется навсегда (в профиле `[select (no cases)]`).

### 10.3 Таймеры

- `time.After(d)` возвращает канал, в который через `d` придёт значение.
- С Go 1.23 таймер, на который больше нет ссылок, собирается GC, даже если не сработал и не остановлен. Раньше `time.After` в горячем цикле держал память до срабатывания.
- В циклах аккуратнее `t := time.NewTicker(d); defer t.Stop()` (Task 5 `startTicker`) или `time.NewTimer` + `Stop` (Task 6).

### 10.4 `context.Context`

```go
ctx, cancel := context.WithTimeout(parent, 5*time.Millisecond)
defer cancel()                 // ОБЯЗАТЕЛЬНО: освобождает таймер и дочерние контексты (vet: lostcancel)

select {
case <-ctx.Done():             // закрывается при отмене или по таймауту
    return ctx.Err()           // context.Canceled или context.DeadlineExceeded
case v := <-ch:
    ...
}
```
- `context.Background()` — корень. `WithCancel`, `WithTimeout`, `WithDeadline` создают дочерний контекст.
- Отмена идёт **вниз по дереву**: отменили родителя — отменены все дети.
- Соглашения: `ctx` — **первый параметр** функции, его не хранят в структурах.
- Стандартная библиотека понимает `ctx`: `http.NewRequestWithContext`, `db.QueryContext`, `exec.CommandContext`. В HTTP-обработчике `r.Context()` отменяется, когда клиент отключился.

## 11. Утечки горутин

### 11.1 Что это и почему опасно

**Утечка горутины** — горутина, которая ждёт то, что **никогда не случится**. Убить её нельзя (раздел 2.5), поэтому она живёт до конца процесса. Вместе с ней живут:
- её стек (≥2 KB);
- **всё, на что ссылается стек**. Стек живой горутины — это **корень для GC** (Week 7), поэтому эти объекты достижимы и не освобождаются. Task 6: каждая зависшая горутина держит отчёт на 64 KB, и память растёт на 64 MB за раунд.

Сервер, который теряет горутину на каждый таймаут, через часы или дни падает по нехватке памяти.

### 11.2 Типичные причины

```go
// 1. Отправка, которую никто не примет (fetchLeaky, handleLeaky)
ch := make(chan int)
go func() { ch <- slowQuery() }()
select { case v := <-ch: ...; case <-time.After(t): return }  // после таймаута ch никто не читает

// 2. Вечный worker без способа остановки (startTickerLeaky)
go func() { for { time.Sleep(d); check() } }()

// 3. Получение из канала, который никто не закроет
go func() { for v := range ch { ... } }()   // если ch не закрыть, горутина ждёт вечно

// 4. Забытый Unlock / Done
mu.Lock(); if err != nil { return }          // следующий Lock ждёт вечно
```

### 11.3 Рантайм видит только полный deadlock

```
fatal error: all goroutines are asleep - deadlock!
```
Это сообщение появляется, только если **все** горутины заблокированы и разбудить их нечему (нет таймеров, сети, сигналов). В сервере всегда есть горутины, которые ждут сеть или таймеры, поэтому утечки **молчат**.

### 11.4 Как найти

| Инструмент | Как | Что видно |
|---|---|---|
| `runtime.NumGoroutine()` | в тестах, в метриках | число растёт и не падает |
| профиль горутин | `pprof.Lookup("goroutine").WriteTo(w, 1)` | сколько горутин стоит на какой строке: «100 @ leak.go:19» |
| то же, `debug=2` | `WriteTo(w, 2)` | каждая горутина + **состояние**: `[chan send]`, `[chan receive]`, `[select]`, `[sleep]`, `[sync.Mutex.Lock]`, `[sync.WaitGroup.Wait]`, `[IO wait]`, `[syscall]`, при долгом ожидании — `[chan send, 5 minutes]` |
| в сервере | `import _ "net/http/pprof"` → `/debug/pprof/goroutine?debug=1` | то же по HTTP |
| в тестах | `go.uber.org/goleak` (`defer goleak.VerifyNone(t)`) | тест падает, если остались горутины |
| в тестах, Go 1.25 | `testing/synctest`: пузырь с фейковым временем | `panic: deadlock: main bubble goroutine has exited but blocked goroutines remain` |
| Go 1.26 (эксперимент `GOEXPERIMENT=goroutineleakprofile`), **Go 1.27** — стабильно | `pprof.Lookup("goroutineleak")`, `/debug/pprof/goroutineleak` | GC находит G, заблокированные на канале или мьютексе, **до которого не может дотянуться ни одна живая G**. Такую G гарантированно никто не разбудит |

Ограничение профиля `goroutineleak`: бесконечный, но **не заблокированный** цикл (`startTickerLeaky`, который просыпается каждые 10 мс) он **не видит**. Формально такая горутина живая (Task 5: нашёл 100 `fetchLeaky` и 0 тикеров).

### 11.5 Правила, которые предотвращают утечки

1. Перед каждым `go` ответь на вопрос: **как и когда эта горутина закончится?**
2. Если результат могут не прочитать, дай каналу **буфер под все отправки** (`make(chan T, 1)` для одной).
3. Долгоживущие горутины принимают `context.Context` (или done-канал) и выходят по `<-ctx.Done()`.
4. Проверяй `runtime.NumGoroutine()` в тестах и смотри профиль горутин в продакшене.

### 11.6 Буфер или `context`? (Task 6)

- **Буфер** убирает утечку: горутина отправляет результат в буфер и завершается. Но она **доделывает всю ненужную работу**: 20 мс ожидания + 64 KB мусора на каждый таймаут.
- **`context`** передаёт отмену **вниз**: работа прекращается сразу, ресурсы освобождаются, запрос к базе отменяется. Буфер при этом всё равно нужен, потому что горутина отправляет `ctx.Err()`, который уже никто не читает.

## 12. Тесты и бенчмарки в этой лабе

```
go test ./...                                        # все тесты
```

**`isPrime`** ([строка 22](task1/main.go#L22)) — перебор делителей `d` от 2, пока `d*d <= n`. Специально медленно. Составное число отсекается быстро (на маленьком делителе), а простое `p` требует ~√p делений. Поэтому **большие числа проверять дороже**, и это объясняет дисбаланс кусков.

**`cpuWork`** ([строка 47](task1/main.go#L47)):
```go
results := make([]int, workers)          // у каждой горутины свой элемент → нет гонки
took := make([]time.Duration, workers)   // сколько работала каждая горутина (флаг -v)
for w := 0; w < workers; w++ {
    from, to := N*w/workers, N*(w+1)/workers // последний кусок кончается ровно на N
    wg.Add(1)                                // до go
    go func() {
        defer wg.Done()
        t := time.Now()
        results[w] = countPrimes(from, to)
        took[w] = time.Since(t)
    }()
}
wg.Wait()                                // после Wait все results[w] видны (happens-before)
```
- **Почему `N*w/workers`, а не `chunk := N/workers`:** если `N` не делится на `workers`, остаток теряется. При 7 горутинах `6 000 000 / 7 = 857 142`, а `7 × 857 142 = 5 999 994`, то есть 6 чисел не проверились бы. Формула `N*w/workers` покрывает всё без дыр.
- **`from, to` вычисляются вне горутины**, а в замыкании `w` своя для каждой итерации (Go 1.22+).
- **Время** меряется от старта до `wg.Wait()`. Оно равно времени **самой медленной** горутины.

**`ioWork`** ([строка 71](task1/main.go#L71)) — `workers` горутин спят по 100 мс. Sleep — это ожидание, CPU не нужен, поэтому 1 и 1000 горутин укладываются в ~100 мс.

## 14. Вопросы к защите — развёрнутые ответы

**1. Чем concurrency отличается от parallelism? Пример каждого.**
Concurrency — структура программы: независимые задачи, которые продвигаются, не ожидая друг друга. Parallelism — одновременное исполнение на нескольких ядрах. Concurrency без parallelism: сервер на 1 CPU, 1000 запросов ждут базу; пока одна горутина ждёт, другая работает, но в каждый момент выполняется только одна. Parallelism: 8 запросов одновременно считают bcrypt на 8 ядрах. Concurrency позволяет распараллелить, но не обязывает. I/O-bound работе хватает concurrency (Task 1: 1000 «запросов» за 100 мс даже при `GOMAXPROCS=1`), CPU-bound нужен parallelism (при `GOMAXPROCS=1` ускорения нет).
*Показать:* `GOMAXPROCS=1 /tmp/demo` и `/tmp/demo`.

**2. Что происходит с горутинами, когда `main` возвращается?**
Программа завершается, все остальные горутины останавливаются мгновенно, где бы они ни были. Их `defer` не выполняются. Поэтому `main` обязана ждать: `WaitGroup`, канал, `errgroup`.
*Показать:* `go run ./task2 say` — строк `goroutine` нет вообще. `saysleep` — пропадает `goroutine 2`.

**3. Почему `wg.Add(1)` вызывают до `go`, а не внутри горутины?**
Горутина может ещё не начать выполняться, когда `main` дойдёт до `Wait`. Если `Add` внутри горутины, счётчик в этот момент может быть 0, и `Wait` сразу вернётся, не дождавшись работы. `Add` до `go`, в родителе, гарантирует, что счётчик увеличен раньше, чем кто-то может вызвать `Wait`. `go vet` с Go 1.25 ловит эту ошибку, а `wg.Go(f)` делает всё сам.
*Показать:* `go run ./task2 broken`, `go vet ./task2`.

**4. Что такое data race? Как его найти?**
Две горутины одновременно обращаются к одной переменной, хотя бы одна пишет, и нет синхронизации (happens-before). Последствия: потерянные обновления (`counter++` — это read, add, write), разорванные многословные значения, `fatal error: concurrent map writes`. Найти: `go run -race`, `go test -race`. Детектор печатает оба стека и завершает программу с кодом 66, но находит только гонки, которые случились в этом запуске. Исправить: `atomic`, `Mutex`, каналы, или не делить данные (`results[i]`).
*Показать:* `go run -race ./task2 broken`, затем `go run -race ./task2 atomic`.

**5. Почему горутины дешевле потоков ОС?**
(1) Стек 2 KB, растёт копированием, а у потока 1–8 MB фиксированного стека. (2) Горутины создаёт и планирует рантайм в user space, без системных вызовов. (3) Переключение — это сохранить пару регистров в известной точке, а не переход в ядро с полным сохранением состояния. (4) Блокировка на канале или в сети не занимает поток. Мои цифры: ≈ 2.7 KB и ≈ 0.2 мкс на горутину, миллион горутин ≈ 2.6 GB. Но горутина не бесплатна: в 300 раз дороже вызова функции, поэтому по горутине на крошечную задачу запускать нельзя (Task 7).
*Показать:* `go run ./task3`, `go test -run '^$' -bench . -benchmem ./task3`.

**6. Что такое G, M, P? Что контролирует `GOMAXPROCS`?**
G — горутина (функция + стек + состояние). M — поток ОС, исполняет код. P — разрешение выполнять Go-код плюс ресурсы: локальная очередь (256 + `runnext`), кэш памяти, таймеры. M исполняет Go-код, только держа P. `GOMAXPROCS` = число P = сколько горутин **одновременно выполняют Go-код**. По умолчанию число ядер, с Go 1.25 на Linux — CPU-лимит контейнера. Потоков может быть больше `GOMAXPROCS`: M в syscall не держат P.
*Показать:* `GOMAXPROCS=2 GODEBUG=schedtrace=1000 /tmp/sched busy` и разобрать строку.

**7. Что такое work stealing? Что происходит при блокирующем системном вызове?**
Work stealing: P с пустой очередью сам ищет работу — глобальная очередь, netpoller, потом **крадёт половину** локальной очереди у случайного другого P. Центрального распределителя нет, а все ядра заняты. Блокирующий syscall: G уходит в ядро вместе со своим M. Через ~20 мкс `sysmon` забирает P и отдаёт его другому M (спящему или новому), и остальные горутины продолжают работать. Когда syscall вернётся, G попробует получить P обратно, иначе встанет в глобальную очередь, а M уснёт. Поэтому 100 блокирующих вызовов создали ~100 потоков, а 100 `time.Sleep` — ни одного: спящая G паркуется и поток не держит.
*Показать:* `/tmp/sched threads`.

**8. Что такое вытеснение и что изменилось в Go 1.14?**
Вытеснение — рантайм забирает CPU у горутины, которая работает слишком долго (>10 мс), чтобы дать поработать другим и чтобы GC мог остановить мир. До 1.14 оно было только кооперативным: проверка в прологе функции. Цикл без вызовов функций держал P вечно, подвешивая и другие горутины, и GC. С 1.14 есть асинхронное вытеснение: `sysmon` посылает потоку сигнал `SIGURG`, обработчик в безопасной точке сохраняет регистры и переключает горутину.
*Показать:* `/tmp/sched preempt` и `GODEBUG=asyncpreemptoff=1 /tmp/sched preempt` (висит, Ctrl+C).

**9. Что такое утечка горутин? Две причины и два способа найти.**
Горутина, которая ждёт то, что никогда не случится. Убить её нельзя, поэтому она живёт вечно и держит стек и всё, на что он ссылается (GC root). Task 6: +1000 горутин и +64 MB за раунд.
Причины:
1. отправка в небуферизованный канал, который больше никто не читает (`fetchLeaky`);
2. бесконечный worker без способа остановки (`startTickerLeaky`);
3. также `range` по каналу, который никто не закроет, и забытый `Unlock`/`Done`.

Найти:
1. `runtime.NumGoroutine()` в тестах и метриках;
2. профиль горутин `pprof.Lookup("goroutine")` / `/debug/pprof/goroutine?debug=1|2`: строка и состояние, где висят горутины;
3. `goleak` или `synctest` в тестах;
4. профиль `goroutineleak` в Go 1.27.

Лечение: буфер под все отправки, `context` с выходом по `ctx.Done()`.
*Показать:* `go run ./task5 -profile 1`, `go run ./task5 -leakprofile`, `SHOW_LEAK=1 go test -run Leaky -v ./task5`, `go run ./task6 leaky` vs `ctx`.

## 15. Дополнительные вопросы, которые могут задать

**Про горутины и WaitGroup**
- *`go f(x)` и `go func(){ f(x) }()` — в чём разница?* — В первом случае `x` вычисляется сразу, при `go`. Во втором замыкание читает переменную `x` позже, и если её меняют, это гонка.
- *Можно ли узнать ID горутины?* — Нет, специально, чтобы не было goroutine-local storage.
- *Можно ли остановить горутину снаружи?* — Нет. Только попросить (`ctx`, закрыть канал). `runtime.Goexit()` останавливает только **текущую** горутину, её `defer` выполняются.
- *Что будет при лишнем `wg.Done()`?* — `panic: sync: negative WaitGroup counter`.
- *Можно ли передать `WaitGroup` по значению?* — Нет: копия — другой счётчик, `Wait` повиснет. vet: `passes lock by value`.
- *Зачем `defer wg.Done()`, а не просто в конце?* — Сработает при любом выходе: раннем `return`, панике с `recover`.
- *Что делает `wg.Go`?* — Go 1.25: `Add(1)` + `go` + `defer Done()` в одном вызове.

**Про гонки**
- *Чем `atomic` отличается от `Mutex`?* — `atomic` — одна аппаратная неделимая операция над одним словом, без блокировок. `Mutex` защищает произвольный участок кода и несколько полей, но может блокировать горутину.
- *Почему `results[i]` из разных горутин — не гонка?* — Разные элементы — разные ячейки памяти. Читаем после `Wait`, а он даёт happens-before.
- *Почему race detector может не найти гонку?* — Он видит только гонки, которые случились в этом конкретном запуске.
- *Можно ли поймать `concurrent map writes` через `recover`?* — Нет, это fatal error, а не паника.
- *Почему одновременная запись в `strings.Builder` при `GOMAXPROCS(1)` — гонка?* — Гонка определяется отсутствием синхронизации, а не реальной одновременностью. Горутину могут вытеснить посреди записи, и порядок ничем не гарантирован.

**Про планировщик**
- *Почему больше горутин, чем ядер, не ускоряет CPU-работу?* — Одновременно работают только `GOMAXPROCS` горутин, остальные ждут в очереди.
- *Что будет, если `GOMAXPROCS` больше числа ядер?* — Больше P, чем ядер. ОС будет переключать потоки, CPU-работа не ускорится и может замедлиться. В контейнере с низким лимитом — троттлинг CFS (поэтому Go 1.25 учитывает лимит).
- *Почему сеть не создаёт потоки, а файлы создают?* — Сеть идёт через netpoller (kqueue/epoll): G паркуется. Обычный файловый ввод-вывод — блокирующий syscall, и M занят.
- *Что такое `runnext`?* — Слот P для последней созданной или разбуженной G. Она запускается первой и в оставшийся квант создателя (producer → consumer, горячий кэш).
- *Что такое spinning thread?* — M без работы, который не уснул, а активно ищет G, чтобы быстро подхватить новую работу. Таких не больше половины занятых P.
- *Что делает `sysmon`?* — Отдельный M без P: отбирает P у syscall, вытесняет G после 10 мс, опрашивает сеть, запускает GC раз в 2 минуты.
- *Куда попадает вытесненная горутина?* — В глобальную очередь.
- *Сколько горутин можно запустить?* — Ограничивает только память: ~2.7 KB на горутину, миллион ≈ 2.6 GB (Task 3).
- *Почему кооперативного вытеснения было мало?* — Цикл без вызовов функций не имеет точек проверки, поэтому P не освобождался. Подвисали и другие горутины, и GC (stop-the-world ждал этот цикл).
- *Почему именно `SIGURG`?* — Приложения его почти не используют, по умолчанию он безвреден, отладчики к нему нормально относятся.

**Про утечки и каналы**
- *Почему буфер 1 спасает `fetchLeaky`?* — Отправка в канал с местом в буфере не ждёт получателя. Горутина отправляет и завершается, а непрочитанный канал соберёт GC.
- *А если отправок две, а буфер 1?* — Вторая отправка снова повиснет. Буфер должен вмещать **все** отправки, результат которых могут не прочитать.
- *Почему leaky-сервер растёт по памяти?* — Стек зависшей горутины — корень для GC, он ссылается на 64 KB отчёт, и отчёт нельзя освободить.
- *Почему рантайм не сообщает об утечках сам?* — `all goroutines are asleep` срабатывает, только если заблокированы **все** горутины. В сервере всегда кто-то ждёт сеть или таймер.
- *Что найдёт `goroutineleak`, а что нет?* — Найдёт горутины, заблокированные на каналах и мьютексах, до которых никто живой не может дотянуться. Не найдёт бесконечный, но активный цикл (тикер).
- *Зачем `defer cancel()`, если таймаут и так сработает?* — Освободить таймер и ресурсы контекста **сразу**, а не через `timeout`, и отменить дочерние операции. `go vet` (lostcancel) ругается, если `cancel` не вызван.
- *Что лучше для Task 6 — буфер или `ctx`?* — Нужны оба. Буфер убирает утечку, `ctx` останавливает ненужную работу (0 отчётов вместо 3000, 1 MB вместо 64 MB мусора за раунд).

**Про Task 7**
- *Почему `parts=2` на 2 ядрах даёт 1.58×, а не 2×?* — Второй кусок дороже на 50%: большие числа. Время = самый долгий кусок. Потолок 1.66×.
- *Почему `parts=8` ближе к 2×?* — Куски раздаются динамически (очередь + work stealing). Простой в конце — не больше одного маленького куска.
- *Почему `parts=200000` медленнее всего?* — На горутину 19 нс работы против ~130–230 нс накладных расходов, плюс 14 MB аллокаций и общий счётчик `WaitGroup`, который дерётся за одну кэш-линию.
- *Почему при `-cpu 1` он ещё медленнее (72 мс)?* — Горутины не успевают выполняться, пока `main` их создаёт. Одновременно живут до 84 000 штук со своими стеками (+150 MB), и переиспользования стеков нет.
- *Сколько горутин оптимально?* — Столько, чтобы занять все ядра и сгладить неравномерность (в разы больше NumCPU), но чтобы на каждую приходились хотя бы десятки микросекунд работы. У меня лучшее — `parts=1000` (0.96 мс, 4.0× на 10 ядрах).
